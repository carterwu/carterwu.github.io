# AI 时代怎么评估代码能力
## 不看“写得多快”，看“能不能稳稳交付”

- 受众：非计算机专业同学
- 风格：轻快、口语化、校园分享风
- 建议总时长：27-30 分钟（中等语速）

讲者备注（0.5 分钟）：
今天这场分享不需要编程背景。我们只回答一个问题：同样都用了 AI，谁是真的会做工程，谁只是把答案粘贴进来？

---

# 先想一个生活场景

- 两组同学都做出了“能点、能用”的作品
- A 组一演示就报错
- B 组稳定运行，还能解释为什么这样设计
- 你会给谁更高分？

讲者备注（1 分钟）：
我们的评估目标，就是把这种“直觉上的差距”变成可解释、可复核的标准。

---

# 先把术语翻成大白话

- `Read-Only 评估`：只“看作业”，不“跑作业”
- `Agent 评估`：真的把代码跑一遍
- `Hybrid`：先快筛，再精查
- `Diff`：这次改了什么
- `Commit`：一次提交记录

讲者备注（1 分钟）：
这页非常关键，先把词讲明白，后面大家就不会被英文术语劝退。

---

# 三份材料，三层逻辑

- 依据：`what-to-eval.md`（我们看哪些证据）
- 方法：`vibe-coding.md`（我们怎么评）
- 标准：`engineer_level.md`（我们按什么打分）

一句话：
先有证据，再有方法，最后有分级。

讲者备注（1 分钟）：
这三份文档像“量尺 + 方法 + 评分表”，缺一个都不公平。

---

# 为什么“代码看起来不错”已经不够

- AI 可以很快写出“看起来很整齐”的代码
- 但“好看”不等于“好用”，更不等于“长期稳定”
- 真正要评的是：遇到问题时，这个人会不会定位、修复、复盘

讲者备注（1.5 分钟）：
就像写论文，排版好看不代表论证扎实。代码也一样。

---

# 依据层：我们到底看什么

- 看改动：是不是一次只解决一类问题
- 看上下文：新代码有没有和旧系统“接上”
- 看目录结构：项目是不是一团乱麻
- 看时间线：是不是一直在“修了又坏、坏了再修”

讲者备注（1.5 分钟）：
我们不是凭感觉打分，是根据仓库里的公开证据说话。

---

# 数据怎么拿（what-to-eval）

- 要验证能不能运行：下载源码后执行
- 只做能力评估：拉取改动记录和代码上下文
- 原则：够用就好，不做无效消耗

讲者备注（1.5 分钟）：
评估不是越重越好，关键是“按问题选工具”。

---

# 方法 1：只读评估能做什么

- 看结构是否清晰
- 看提交是否规范
- 看有没有测试意识
- 快速筛选大量仓库

讲者备注（1 分钟）：
它像“阅卷第一轮”，快而且省资源。

---

# 方法 2：只读评估看不到什么

- 看不到代码是否真的能跑
- 看不到测试是否真的通过
- 看不到运行时问题（卡死、泄漏、冲突）

讲者备注（1 分钟）：
所以只读评估不能单独决定最终结论。

---

# 方法 3：Agent 评估补上真相

- 真跑编译和构建
- 真跑测试
- 真看运行稳定性
- 真看安全和静态检查结果

讲者备注（1.5 分钟）：
Agent 评估更像“实操考试”，能看到真实表现。

---

# 推荐做法：Hybrid（先筛后验）

- 第一步：只读评估，先筛掉明显问题
- 第二步：Agent 评估，重点样本深入验证
- 第三步：定期对齐两种结果，防止偏差

讲者备注（1.5 分钟）：
这套组合兼顾效率和准确性，特别适合教学场景。

---

# 代码示例 1：坏 vs 好（异常处理）

坏例子（能跑，但一报错就崩）：
```js
async function loadUser(id) {
  const res = await fetch(`/api/user/${id}`)
  const data = await res.json()
  return data.name.toUpperCase()
}
```

好例子（考虑失败场景）：
```js
async function loadUser(id) {
  try {
    const res = await fetch(`/api/user/${id}`)
    if (!res.ok) return "用户暂时不可用"
    const data = await res.json()
    return (data?.name ?? "匿名用户").toUpperCase()
  } catch {
    return "网络异常，请稍后重试"
  }
}
```

讲者备注（2 分钟）：
差别不在“能不能运行”，而在“出问题时会不会兜底”。工程里，兜底能力就是分数。

---

# 代码示例 2：坏 vs 好（测试质量）

坏例子（有测试文件，但几乎没价值）：
```js
test("formatPrice works", () => {
  expect(true).toBe(true)
})
```

好例子（验证真实行为和边界）：
```js
test("formatPrice formats normal numbers", () => {
  expect(formatPrice(12.5)).toBe("¥12.50")
})

test("formatPrice handles invalid input", () => {
  expect(formatPrice(null)).toBe("¥0.00")
})
```

讲者备注（2 分钟）：
有测试不代表会测试。我们看的是“有没有测到关键风险点”。

---

# 代码示例 3：坏 vs 好（可维护性）

坏例子（所有事都塞进一个函数）：
```js
function submitOrder(order) {
  // 参数检查、算价格、发请求、写日志、更新 UI 全在这里
}
```

好例子（拆成清晰模块）：
```js
function validateOrder(order) { /* ... */ }
function calculateTotal(order) { /* ... */ }
async function createOrder(order) { /* ... */ }
function updateOrderUI(result) { /* ... */ }
```

讲者备注（2 分钟）：
这像写小组作业分工。分工清晰，后面接手的人才不会痛苦。

---

# 评分标准：L1 到 L5（通俗版）

- L1：会复制，不太会判断
- L2：能独立完成功能
- L3：一个人能快速做出完整原型
- L4：能把系统做稳、做久、做可维护
- L5：能制定规则，带动团队和社区

讲者备注（1.5 分钟）：
等级不是“聪不聪明”，而是“能稳定承担多大责任”。

---

# 9 个维度，不用背，记住四大块

- 代码质量：需求对齐、测试深度、可复现
- 系统能力：部署、架构演进、老系统改造
- AI 能力：工具编排、自动反馈闭环
- 职业能力：协作、文档、开源贡献、底层理解

讲者备注（1.5 分钟）：
四大块就像体测：速度、力量、耐力、协调，不是只看单项。

---

# 重点信号：看“成长轨迹”，不是看单次截图

- 高风险模式：`feature -> fix -> fix -> fix`
- 好信号：一次定位根因，修复链条短
- 所以我们看“连续提交行为”，不只看一个 commit

讲者备注（1.5 分钟）：
一次做对可能是运气，多次做对才是能力。

---

# 课堂可直接用的权重建议

- `40%` 代码质量与测试
- `25%` 架构与部署能力
- `20%` AI 工程化能力
- `15%` 协作与职业素养

讲者备注（1 分钟）：
这个权重对非科班同学也友好，因为它奖励“过程质量”和“稳定交付”。

---

# 课堂评估 7 步流程

1. 先定评估周期（比如最近 30 天）
2. 收集改动证据（Diff + 上下文 + 目录）
3. 先做只读初筛
4. 再做重点样本执行验证
5. 按 L1-L5 + 9 维评分
6. 给出“有证据”的反馈
7. 布置下一轮改进任务

讲者备注（1.5 分钟）：
要让学生知道“分数从哪来、怎么提高”，透明才有说服力。

---

# 反馈模板（老师助教可直接套）

- 观察：哪里做得好，哪里有风险
- 证据：对应提交记录或代码片段
- 结论：当前大致等级
- 行动：下一周最该做的 1-2 件事

讲者备注（1 分钟）：
反馈尽量具体，不用“你不行”，要说“你下一步怎么行”。

---

# 可以直接说的校园风话术

- “能跑只是及格，稳定才是高分。”
- “我们不比谁写得快，我们比谁改得稳。”
- “AI 是队友，不是甩锅对象。”
- “真正的高手，能解释自己为什么这么改。”

讲者备注（1 分钟）：
口语化表达能降低焦虑，让非技术同学也敢参与。
