# AI 时代代码评估怎么做
## 用“证据”看能力，而不是只看代码长相

- 场景：课程答辩 / 技术分享 / 校园 workshop
- 风格：轻快口语化、校园风
- 建议总时长：25-29 分钟（中等语速）

讲者备注（0.5 分钟）：
今天我们不卷术语，讲一件实事：AI 把“写出一段像样代码”这件事变容易了，那我们怎么公平评估一个人的工程能力？答案是看证据链。

---

# 先问一个问题

- 两位同学都用了 AI，代码都“看起来很像”
- 一个同学上线后频繁修 bug
- 另一个同学上线稳定、可维护、可扩展
- 我们怎么区分？

讲者备注（1 分钟）：
在 Vibe Coding 时代，代码外观越来越像，真正拉开差距的，是“谁在掌控系统”，而不是“谁复制得更快”。

---

# 今天的主线：三份材料，三层逻辑

- 评估依据（Evidence）：`what-to-eval.md`
- 评估方法（Method）：`vibe-coding.md`
- 评估标准（Rubric）：`engineer_level.md`

一句话版本：
先拿到可信证据，再用对方法，最后按统一标准打分。

讲者备注（1 分钟）：
这三份文档不是并列关系，而是流水线关系。没有证据，标准就会飘；只有方法没标准，结论就不稳定。

---

# 为什么传统评估不够用了

- 指标失真：代码行数、提交频率不再可靠
- AI 能快速产出“可读但未必正确”的代码
- 评估重点转移：从“写代码”转向“筛代码、验代码、改代码”

讲者备注（1.5 分钟）：
以前我们看“你写了多少”，现在要看“你判断了什么、拒绝了什么、修正了什么”。工程师角色从作者变成了策展人+验证者。

---

# 依据层：我们到底看什么证据

- Diff：改动质量、是否原子化、有没有边界处理
- File Context：改动是否融入上下文，不是硬贴补丁
- Repo Tree：结构是否清晰，职责是否分离
- Commit 序列：有没有“反复试错但不定位根因”的循环

讲者备注（1.5 分钟）：
这里强调“证据可公开复核”。我们尽量基于 Git 平台可见信息，减少主观印象打分。

---

# 数据获取策略（what-to-eval）

- 需要运行代码：用 Archive API 拉源码到本地
- 只做代码评估：用 REST API 精准拉 Diff + 上下文
- 不一刀切：按任务选最省资源的方法

关键结论：
评估文本不等于运行代码，二者要分流。

讲者备注（1.5 分钟）：
跑测试要文件系统，LLM 读文本只要上下文。把两件事混在一起做，会浪费大量算力和时间。

---

# 方法层（1）：Read-Only 评估能做什么

- 架构与模块边界判断
- 改动质量与提交纪律判断
- 测试习惯与类型安全信号判断
- 可扩展到大规模候选仓库初筛

讲者备注（1.5 分钟）：
Read-Only 的强项是“快、便宜、可扩展”。尤其适合先筛一遍，把明显不达标的样本提前过滤。

---

# 方法层（2）：Read-Only 的天花板

- 看得到“写了测试”，看不到“测试是否真过”
- 看得到“结构像对”，看不到“运行是否真对”
- 看不到运行时问题：死锁、泄漏、依赖冲突

讲者备注（1 分钟）：
AI 生成代码很会“长得正确”，这就是只读评估最容易被欺骗的地方。

---

# 方法层（3）：Agent 评估补上什么

- 编译/构建是否通过
- 测试是否通过，覆盖是否有效
- 运行时行为是否稳定
- 静态分析与安全扫描是否告警

讲者备注（1.5 分钟）：
Agent 评估拿到的是“可执行真相”，代价是更高的基础设施成本和安全隔离要求。

---

# 推荐策略：Hybrid（先筛后验）

- 第一步：Read-Only 初筛（快）
- 第二步：Agent 定点验证（准）
- 第三步：定期校准两者一致性（稳）

一句话：
先用便宜方法找候选，再用昂贵方法确认真相。

讲者备注（1.5 分钟）：
这个组合非常适合教学或团队评审：既能规模化，又不会被“看起来不错”的代码骗过去。

---

# 标准层：L1-L5 五级画像（engineer_level）

- L1 理论认知：高度依赖 AI，缺乏判断
- L2 独立实践：可交付基本功能
- L3 一人全栈：能闭环做 MVP，效率高
- L4 团队基石：强调质量门禁与长期稳定
- L5 领导者：定义模式与生态影响力

讲者备注（2 分钟）：
这五级不是“谁更会写提示词”，而是“谁更能稳定地产生工程价值”。

---

# 9 个评估维度，一图看全

- 规格实现与内建质量：需求对齐、测试深度、可复现性
- 云原生与架构演进：部署优化、遗留系统现代化
- AI 工程与自动进化：智能体编排、数据闭环
- 工程底座与职业操守：开源贡献、手动掌控力

讲者备注（2 分钟）：
课堂里不一定每次都打满 9 维，但要有“全景地图”，否则大家会只卷某一项，比如只卷模型调用。

---

# 从“看代码”升级到“看轨迹”

- 关键信号：Fix-Cycle Depth（修复链深度）
- 典型模式：Feature → fix → fix → fix（风险高）
- 高水平特征：快速定位根因，修复次数少

讲者备注（1.5 分钟）：
轨迹比截图更说明问题。一次提交好看不代表稳定，连续多次无效修补才是能力短板的真实信号。

---

# 给课程落地的打分建议（可直接用）

- `40%` 工程质量：需求对齐、测试深度、可复现性
- `25%` 架构与演进：结构设计、遗留改造、部署策略
- `20%` AI 工程能力：工具编排、反馈闭环
- `15%` 职业能力：协作、文档、开源与底层掌控

讲者备注（1.5 分钟）：
这是一套“教学友好型权重”。如果是生产团队，可适当提高运行稳定和安全相关权重。

---

# 评估流程（课堂版 7 步）

1. 锁定评估周期（例如最近 30 天）
2. 拉取 Diff、文件上下文、目录结构
3. 做 Read-Only 初筛
4. 对高潜样本做 Agent 执行验证
5. 按 L1-L5 + 9 维打分
6. 给出证据化反馈（附 commit/PR 片段）
7. 给出下一阶段改进任务

讲者备注（2 分钟）：
重点是“可复现”。同一个样本，换助教评，结论不应差太多。

---

# 示例：一条“证据化反馈”该怎么写

- 观察：测试文件存在，但断言强度低，边界值缺失
- 证据：3 个功能提交无配套异常路径测试
- 结论：当前在 L2-L3 之间，交付可用但稳定性不足
- 行动：补齐超时、空值、异常输入三类用例

讲者备注（1.5 分钟）：
反馈要像教练，不像法官。指出问题同时给可执行动作，学生才会进步。

---

# 校园风表达模板（可直接照着讲）

- “这段代码能跑，不等于能交付。”
- “我们不只看你写得快不快，更看你改得稳不稳。”
- “真正的高手不是不出错，是能快速定位并复盘。”
- “AI 是你的外骨骼，不是你的大脑外包。”

讲者备注（1 分钟）：
口语化不是降标准，而是把高标准讲得更容易吸收。

---

# 一页总结

- 用 `what-to-eval` 保证评估有证据
- 用 `vibe-coding` 决定评估方法（Read-Only / Agent / Hybrid）
- 用 `engineer_level` 统一等级与维度
- 最终目标：评估“工程判断力”，而不是“AI 生成速度”

讲者备注（1 分钟）：
一句收尾：代码可能是 AI 写的，但工程责任永远属于人。

---

# Q&A

- 可以从你们课程项目里现场抽一个 PR，按这套框架试评分
- 也可以先从 3 个样本做小规模试跑，再全班推广

讲者备注（0.5 分钟）：
建议现场挑一个真实样本做 5 分钟演示，大家会立刻明白“证据化评估”怎么落地。
